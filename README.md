# keep-truth

在长流程复杂任务中维持一条干净、真实、不跑偏的主线。

`keep-truth` 是一个用于复杂任务的 Agent Skill。它让主 Agent 围绕明确的目标，只带着必要状态与已核验结论继续推进，将探索、补证和重试留在独立的局部上下文中。

主 Agent 就是与你直接对话、负责组织任务和决定下一步的 Agent。

当前版本：**0.2**。

## 设计理念

复杂任务需要不断探索，但主 Agent 做下一步判断时，并不需要带着所有探索过程。

随着任务推进，猜测、失败尝试、重复材料和局部问题容易一起进入上下文。主 Agent 既要记住原始目标，又要从大量过程信息中辨认事实，容易出现方向漂移、未经核验的判断被反复引用等问题。

`keep-truth` 围绕三个原则展开：

- **目标有锚点。** 原始目标、成功标准、非目标和关键约束单独保存，避免被后续讨论悄悄改写。
- **结论有依据。** 探索与核验分别承担职责，主 Agent 接收经过核验的结论、证据、适用边界和剩余缺口。
- **状态反映当前情况。** 保留仍影响决策的事实、未决问题和下一步，移除失去价值的内容，避免状态文件变成另一份完整聊天记录。

这三个原则共同约束任务如何推进：目标不被过程改写，猜测不被当作事实，主 Agent 不被探索噪声拖离主线。

“干净”指信息有边界、事实有依据。证据不足、证据冲突及影响结果的阻塞，仍然必须交付给主 Agent，不能为了让摘要简洁而被隐藏。

## 适用场景

适合目标明确、需要多轮探索与核验的任务：

| 场景 | 典型用法 |
| --- | --- |
| 陌生项目调研 | 理解项目结构、核心模块、业务流程与依赖关系 |
| 复杂需求与系统分析（系分） | 沿需求追踪代码与配置，梳理现状、影响范围、约束和缺口 |
| 复杂技术推理 | 围绕一个问题逐步取证，区分事实、推断与尚未确认的内容 |
| 技术决策辅助 | 核验方案判断所依赖的事实，由主 Agent 结合目标与约束作取舍 |

例如，可以要求它协助完成支付幂等系分、梳理订单状态流转，或调研一次接口改造会影响哪些模块。

简单问答、单点修改等任务通常不需要完整角色链。是否启用由用户显式决定。

## 设计核心思路

### 1. 分开保存目标和当前状态

目标需要保持稳定，推进状态则需要持续更新。将两者混在长篇过程记录里，很难看清现在为什么做、做到哪、还缺什么。

因此，每个需求在目标项目根目录下拥有独立工作区，用三个文件分别保存目标、当前状态和外部产物入口：

```text
.kt/{requirement_name}/
  GOAL.md
  FOCUS.md
  MANIFEST.md
```

三个文件固定存在，职责互不替代：

| 文件 | 核心职责 | 内容与维护方式 |
| --- | --- | --- |
| `GOAL.md` | 固定原始目标锚点 | 只保存原始目标、成功标准、非目标和关键约束；用户明确改变目标时追加变更记录 |
| `FOCUS.md` | 保存当前推进状态 | 包含当前目标、仍影响决策的已确认事实、未决问题、下一步和必要引用；每轮整体重写 |
| `MANIFEST.md` | 提供外部产物入口 | 只登记产物、回答的问题、路径与可用状态；可以为空，不保存结论正文 |

过程记录、代码事实和阶段结论不写入 `GOAL.md`。`FOCUS.md` 不追加历史，也不保存完整探索过程。引用指针用于定位证据，便于后续核验。

### 2. 将探索留在局部，把核验结果交给主 Agent

探索可能经历失败、重试和换路径。这些过程需要发生，但不必全部进入主 Agent 的上下文。`keep-truth` 将探索、核验和决策分开，通过三种角色控制信息交接：

```text
主 Agent
  │ 任务卡
  ▼
核验 Agent ↔ 探索 Agent
  │ 结果卡
  ▼
主 Agent
  ├─ 判断下一步
  ├─ 更新 FOCUS.md
  └─ 需要时发起产物维护
```

| 角色 | 负责什么 | 交接边界 |
| --- | --- | --- |
| 主 Agent（Decision Lead） | 读取目标与当前状态、派发任务、决定下一步 | 只消费核验后的结果卡，不直接读取探索过程 |
| 探索 Agent（Scout） | 在明确边界内探索代码、文档、配置或数据，提供原始证据 | 只向核验 Agent 交付，不继承完整主对话、不自行扩展目标 |
| 核验 Agent（Reviewer） | 核验证据、补齐缺口、判断事实与适用范围，并收口任务 | 只向主 Agent 交付最终结果卡，不替它做方案取舍 |

核验 Agent 可以与探索 Agent 多轮补证。过程噪声留在局部，影响最终判断的限制与缺口保留在结果中。

### 3. 用两类卡片约束交接

角色分开后，还需要限制交接内容，避免完整聊天记录或未经核验的判断被重新传递。

- **任务卡（Task Card）** 明确一个要回答的问题，附上必要的已确认事实、证据要求、探索边界和完成标准。下游据此开展工作，不自行扩大目标。
- **结果卡（Result Card）** 交付经过核验的结论及证据，说明适用边界、剩余缺口，以及是否影响原始目标。主 Agent 据此判断下一步。

例如，调查支付幂等时，任务卡可以限定“只核验补偿入口”。结果卡需要区分“该入口已核验”与“所有支付入口都已核验”，避免局部结论被扩大成全局判断。

证据不足时，明确交付“尚不能确认”及缺口。卡片的固定字段和完整约束见 [SKILL.md](./SKILL.md)。

### 4. 需要时才沉淀外部文件

并非每次探索都需要额外生成文件。`artifacts/` 是可选目录，只有用户要求，或主 Agent 明确需要保存外部文件时，才在需求工作区内创建。产物也可以位于项目已有目录，由 `MANIFEST.md` 按需登记入口。

`artifacts/` 真实存在后，才按需启用索引维护 Agent（Curator），由核验 Agent 管理。它只机械维护索引、指针和状态，不参与推理、不改业务结论。

## 安装与调用

### 1. 安装技能

解压技能包，将整个 `keep-truth` 文件夹放入 Codex 用户技能目录：

| 系统 | 默认安装位置 |
| --- | --- |
| Windows | `%USERPROFILE%\.codex\skills\keep-truth\` |
| macOS / Linux | `~/.codex/skills/keep-truth/` |

如果设置了自定义 `CODEX_HOME`，使用其下的 `skills/keep-truth/`。最终目录应直接包含以下文件，避免多嵌套一层同名目录：

```text
keep-truth/
  SKILL.md
  README.md
  agents/
    openai.yaml
```

安装后重新加载客户端或开启新会话，使其发现技能。已有同名技能时，先确认是否需要替换。

### 2. 显式调用并描述需求

在目标项目的对话中调用。Codex 原生入口为 `$keep-truth`，技能同时将 `/keep-truth` 定义为显式调用口令。

```text
$keep-truth

需求名称：payment-idempotency
目标：基于代码和已有文档，梳理支付回调与补偿入口的幂等保障，并输出一份系分。
成功标准：覆盖相关入口，说明现有保障、证据位置、适用范围与尚未确认的问题。
非目标：不修改业务代码，不进行生产操作。
关键约束：只读已授权的代码和文档；证据不足时明确标注缺口。
```

首次使用时必须由用户给出需求名称 `requirement_name`。没有提供时，代理会先询问；名称应是合法的单个目录名，例如 `payment-idempotency`。

不必手工创建状态文件或填写每一张交接卡片。给定需求后，代理按契约维护工作区、组织探索与核验。目标定义有影响推进的缺口时，会先澄清。

### 3. 围绕当前需求推进

启用后，主 Agent 读取目标与当前状态，派发单问题任务，依据核验结果继续推进，并整体更新 `FOCUS.md`。

你可以继续指定关注点，例如：

```text
继续核验补偿入口与回调入口的幂等约束是否一致，先给出证据与差异。
```

需要交付物时，明确告诉它产物类型与要求，例如“输出一份系分”或“把已经核验的接口影响范围保存为 Markdown”。具体撰写或执行由相应任务单元承担。

默认使用中文维护状态和卡片；需要其他语言时明确说明。技能作用于当前需求，直到需求完成或用户明确退出。

## 注意事项与职责边界

### 它负责什么

`keep-truth` 负责目标约束、主 Agent 的上下文边界、事实与结果交接，以及当前状态维护。它提供组织任务的信息协议；具体问题仍依赖模型、执行工具和可访问的证据来解决。

完整角色链需要所用的 Agent 客户端支持独立上下文子代理、由核验 Agent 创建并管理探索 Agent、定向消息交接，以及项目文件读写。能力不足时，应说明限制，不在同一上下文中轮流扮演角色来冒充隔离。

### 启用与范围：由用户确定需求

- **不自动启用。** 不根据任务看起来复杂就自行启动；讨论、引用或修改技能时提到名称，也不构成启用。
- **不自行命名或合并需求。** 用户确定需求名称，一个需求对应一个工作区。
- **不改写目标或扩大范围。** 不把探索发现自动升级为新目标；用户明确改变目标后，才追加目标变更记录。
- **不扩展执行授权。** 调用技能本身不构成修改业务代码、操作生产或对外发布的授权；执行范围由具体需求与已有授权决定。

### 产物与流程：按实际需要组织交付

- **不自动生成阶段产物。** 不因一轮结束、卡片完成或进入某个阶段，就自动生成报告、方案或其他阶段文件。
- **不默认创建沉淀目录。** 初始化时不创建 `artifacts/`；用户要求或主 Agent 明确需要保存文件时才创建。
- **不接管研发流程。** 不自动推进需求评审、开发、测试、发布等阶段，不绑定 `.aura` 或技术方案模板。

这些边界不影响明确要求的交付：你要求输出系分，它会围绕该交付组织任务；只要求调研时，不会额外套用一整套研发文档流程。

### 事实与决策：核验结果不代替取舍

- **不把探索过程写成事实。** 猜测、失败日志和重试轨迹不进入已确认事实，`FOCUS.md` 不维护为历史流水账。
- **不隐瞒关键缺口。** 结论须说明证据与适用范围；证据不足或存在冲突时，如实交付，不能用确定的语气代替核验。
- **核验 Agent 不替主 Agent 拍板。** 核验角色提供事实、边界和缺口；主 Agent 结合目标与约束决定下一步。

一张结果卡完成交付，只说明该单问题任务已收口。整个需求是否完成，需要对照 `GOAL.md` 的成功标准及用户明确的目标变更判断。

完整规则见 [SKILL.md](./SKILL.md)；显式调用策略见 [agents/openai.yaml](./agents/openai.yaml)。
